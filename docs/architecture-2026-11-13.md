# Архітектурний аналіз Slime Climb (2026-11-13)

Знято з `main` після PR #40. Числа — факти (`wc -l`, `grep`), оцінки позначені окремо.

## Факти
- Код гри: 181 файл, ~13 800 рядків (`src` + `server`). Тести: ~3 750 рядків, 573 тести.
- `src/scenes/GameScene.js` — **1440 рядків**, 73 методи, 61 імпорт, ~180 полів `this.x = …`, `create()` на 213 рядків. Це 10% усього коду в одному класі.
- Наступні за розміром: `Codex.js` 636 (дані довідника), `balance.js` 521 (числа), `ShkodkoBoss.js` 349, `Audio.js` 301, `KazanBoss.js` 267. Решта — до 250.
- `src/systems/*` — чисті функції без Phaser, з тестами (перевіряє `tests/purity.test.js`). Це здорова частина.
- Сутності (`src/entities`) лізуть у сцену напряму: 160 звернень `scene.щось`, 27 різних полів і методів (`nowMs`, `player`, `hurtPlayer`, `spawnEnemy`, `enemyProjectiles`, `bombs`, `biomeIdx`…). Договору, що саме сцена зобов'язана давати, ніде не записано.
- Сцени тестами не покриті. Єдина перевірка — бот (`scripts/playtest.mjs`), і він безсмертний: шлях смерті й GAME OVER не ходить.

## Діагноз
Проблема одна, але росте: `GameScene` — «божественний об'єкт». Кожен етап (зима, Шкодько, бамбук, лава, таблиця) додавав туди 100–200 рядків. Контентний захід фідбеку-6 (переробка Шкодька, сюрикени, снігова куля) додасть ще ~300. Решта проєкту поділена нормально, переписувати її не треба.

Чим це шкодить уже зараз (оцінка):
- правка в одному місці ламає інше: усе ділить ті самі ~180 полів;
- помилку важко локалізувати (глухий GAME OVER шукали по всьому файлу);
- Claude щоразу читає 1440 рядків — це токени й пропущені деталі.

## Ризики рефакторингу
- **Регресії без страховки.** Сцени без тестів, бот не вмирає. Перенесення 1000 рядків «на око» майже напевно щось зламає (порядок оновлення за кадр, відписки від подій при перезапуску сцени).
- **Баланс не перевірений людиною з етапу 10.** Якщо рефакторинг змішати з правками балансу, після тесту буде неясно, що винне.
- **Користі для гравця нуль.** Це плата наперед за наступні етапи. Якщо до релізу лишилось 1–2 заходи, окупиться слабо; якщо ще біоми й боси — окупиться.

## Як робити
1. Спершу страховка: бот учиться вмирати й перезапускати гру (сценарій «смерть → GAME OVER → тап → нова гра» в кожному біомі), `scripts/smoke.mjs` ходить по меню.
2. Один модуль — один PR, **чисте перенесення без зміни поведінки**. Після кожного: тести, збірка, бот у 4 біомах.
3. Порядок: `PauseController` (найменший, перевірити підхід) → `BiomeDirector` → `LootEffects` → `SpawnDirector` → `BossDirector` → `Combat`.
4. Запобіжник уже є: `tests/size.test.js` — жоден файл `src` не довший за 650 рядків; для `GameScene` стеля 1450, після кожного PR її опускаємо.
5. Контентний захід фідбеку-6 — після рефакторингу (або хоча б після `SpawnDirector` і `BossDirector`): Шкодько, сюрикени й снігова куля лягають саме туди.
